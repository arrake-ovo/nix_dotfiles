# `lua/config/colemak.lua`

## 作用

这是整套配置的核心抽象层。它把方向语义从传统的 `h/j/k/l` 改成了更适合你的 Colemak 方案：

- 左：`n`
- 上：`u`
- 下：`e`
- 右：`i`

## 为什么这样写

- 你不是只想改“普通移动”，而是想把整个编辑器的方向语义统一掉。
- 所以这里没有把 Colemak 逻辑散落到每个插件里，而是抽成 `motions`、`apply_list_keys()`、`apply_buffer_keys()` 这样的公共工具。
- 这样后续接入 `snacks`、`trouble`、`mini.files`、`flash` 时，都能复用同一套方向约定。

## 关键设计

### `motions`

把方向抽象成数据，而不是把 `u/e/n/i` 写死在每个文件里。这样所有插件层都只依赖“方向语义”，不依赖具体按键。

### `apply_list_keys()`

这个函数专门解决“列表型界面”的键位映射问题。

原因：

- 插件里的列表窗口很多，像 picker、explorer、qf、dapui 都属于这一类。
- 它们的操作模式高度相似：上一个、下一个、取消、确认。
- 与其每次手写一遍，不如统一复用一个合并函数。

### `apply_buffer_keys()`

这个函数解决的是“某些 filetype 不是通过插件配置暴露键位，而是只能在 buffer 内补映射”的问题。

原因：

- `lazy`、`mason`、`qf`、`dapui_*` 这些窗口不一定都提供统一配置接口。
- 用 `FileType` + buffer-local keymap，可以把 Colemak 语义补到这些界面里。

### `setup()`

这里做了三层事情：

- 重定义基础移动
- 重定义窗口移动
- 给特殊 filetype 补列表移动

这是合理的，因为这三个层面都属于“方向语义统一”这个主题。

## 这份配置背后的取舍

- 保留 `h/j/k/l` 的 Vim 传统会更兼容默认文档，但会让你的肌肉记忆分裂。
- 全量切到 Colemak 虽然一开始更陡，但长期一致性更高。
- 对 `lazy`、`mason` 这类界面保留原生 `h/j/k/l`，说明你在“全局一致性”和“第三方界面兼容性”之间做了折中。
