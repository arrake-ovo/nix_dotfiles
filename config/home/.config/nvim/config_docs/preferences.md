# 个人偏好与快捷键习惯

这份文档不对应某一个单独的 Lua 文件，它用来集中说明这套 Neovim 配置背后的个人偏好。

前面的按文件文档解释的是“哪里改了什么”；这份文档解释的是“为什么整套配置会朝这个方向收敛”。

## 前提：这套配置建立在 Colemak 键盘布局上

理解这套键位前，最重要的前提是：你的日常键盘布局不是 QWERTY，而是 Colemak。

这意味着很多按键位置、手指负担和肌肉记忆，都是围绕 Colemak 来判断的，而不是围绕 Vim 传统的 `h/j/k/l` 或 QWERTY 的字母位置来判断。

所以这套配置不应该被理解成：

- 在标准 QWERTY 上随意重新分配一组按键

而应该被理解成：

- 在 Colemak 布局前提下，为 Neovim 建立一套一致、长期可用的个人操作语言

这也是为什么文档里会反复强调“方向语义”“列表语义”“高频动作前置”。  
这些判断都不是抽象偏好，而是和你实际使用的 Colemak 键盘布局直接相关。

## 方向语义优先于插件默认值

这套配置最核心的偏好，是优先维护一套稳定的方向语义，而不是迁就每个插件各自的默认键位：

- 左：`n`
- 上：`u`
- 下：`e`
- 右：`i`

这组方向不是随便挑出来的，而是结合 Colemak 布局下的按键位置和使用手感确定的。  
这说明你的目标不是“局部改几个按键”，而是让普通移动、窗口移动、列表移动、文件浏览、结果面板尽量共享同一套空间心智。

这样写的好处：

- 不同插件之间切换时，方向判断成本更低。
- 列表、窗口、面板这些“二维界面”更容易形成统一肌肉记忆。
- 后续新增插件时，也更容易判断该怎么接入，而不是每次重新背一套默认键位。

## 列表界面要像列表界面

你对列表型界面的期望很明确：它们应该有统一的操作语言，而不是每个插件一套规则。

当前这套列表偏好大致是：

- `u` / `e`：上一个 / 下一个
- `n`：退出、返回、关闭、退一层
- `i`：进入、确认、打开、进一步查看

这套偏好已经体现在：

- `snacks picker`
- `snacks explorer`
- `mini.files`
- `trouble`
- `which-key` 的翻页

为什么这样设计：

- 这些界面虽然名字不同，本质上都是“列表 + 详情”或“层级 + 进入/退出”。
- 如果每个地方都重新学习一遍默认键，会把注意力浪费在界面适应上。
- 统一之后，插件只是载体，真正被记住的是“列表如何操作”。

## 高频动作前置，低频动作不强行接管

你的配置风格不是“能改的都改”，而是优先把高频动作放到更顺手的位置，同时避免为低频功能引入额外负担。

典型例子：

- `;` 进入命令行
- `q;` 查看命令历史
- `=` / `-` 跳转搜索结果
- `gb` / `gf` 处理跳转历史
- `k` / `K` / `l` 重排为更贴近个人输入习惯的编辑动作

相对地，一些低频或有替代路线的功能不会被过度包装。例如：

- `flash.nvim` 的 `f/F/t/T` 增强没有成为核心方案
- `codelens` 没有被优先纳入主工作流
- `trouble.nvim` 目前更像稳定的结果面板，而不是高度定制的主入口

这反映出你的取舍标准：

- 高频、常用、会反复触发的动作，值得改到更顺手。
- 低频、边缘、已有替代路径的能力，先保守处理，避免系统越来越重。

## 搜索、选择、结果浏览要分层

这套配置不是把所有“跳转”都塞进同一种工具，而是有明确分工：

- `snacks picker`：负责查找、筛选、选择条目
- `trouble.nvim`：负责持续浏览诊断、quickfix、引用等结果
- `flash.nvim`：负责当前屏幕内的快速落点
- `LSP`：负责定义、引用、hover、rename、code action 这些语义能力

为什么要这样分：

- “找东西”和“看结果”虽然相关，但操作节奏不同。
- “文本内跳点”和“语义级跳转”也不是同一种问题。
- 先把工具边界划清，键位系统才不容易打架。

这个偏好也解释了为什么有些键位冲突需要让位给现有体系：你的目标不是让每个插件都抢主入口，而是让每类任务只有一个主要入口。

## 预览默认轻量，进入焦点要显式

你对预览窗口和说明窗口的偏好也很稳定：

- 默认先弹出，不要立刻抢走编辑焦点
- 真正要读的时候，再显式进入那个窗口

这和你对 `picker preview`、`trouble preview`、`LSP hover` 的讨论是一致的。  
你不希望每次查看信息都打断当前编辑流，但又希望需要时能快速进入说明窗口。

这也是为什么当前 LSP 的 `K` 被设计成条件键：

- 如果还没有 hover 窗口，`K` 先打开 hover
- 如果 hover 或 signature 的 `noice` 文档窗口已经存在，`K` 直接把焦点切进去

这样做的原因：

- 保留了 `K` 作为“查看信息”的自然语义
- 又避免额外增加一个必须记忆的焦点切换键
- 让同一个高频键在“第一次查看”和“继续阅读”两个阶段承担连贯动作

## 尽量显式，不依赖隐藏状态

你整体上偏好显式动作：

- 显式指定分屏方向打开
- 显式区分输入区、列表区、预览区
- 显式进入说明窗口，而不是让弹窗自动抢焦点

这说明你的工作流更看重：

- 可预测性
- 低歧义
- 一次按键只表达一个明确意图

所以这套配置虽然改键较多，但并不是“炫技式改键”，而是在尽量减少含糊和意外。

## 这份偏好文档怎么使用

后续如果继续新增插件或调整键位，最好先用这几个问题检查一下：

1. 这个界面属于方向移动、列表浏览、语义跳转里的哪一类？
2. 它应该复用现有的 `n/u/e/i` 语义，还是保留社区通用默认键更划算？
3. 这个动作是高频核心动作，还是低频补充能力？
4. 它应该成为主入口，还是作为现有体系的补充？

只要继续沿着这几个判断标准走，后面的配置通常就不会偏离你现在已经形成的个人手感。
